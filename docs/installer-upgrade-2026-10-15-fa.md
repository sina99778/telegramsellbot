# ارتقای نصب و آپدیت — ۱۵ اکتبر ۲۰۲۶

نسخهٔ نصب‌کننده: `2026-10-15-1`

وابستگی SQLAlchemy نیز با extra رسمی `asyncio` ثبت شده تا نصب تازه، کتابخانهٔ لازم `greenlet` را دریافت کند؛ نبود این وابستگی باعث شکست اجرای تست‌ها در نصب تمیز GitHub شده بود.

## دریافت و اجرا

با کاربر root در سرور اجرا کنید:

```bash
cd /opt/telegramsellbot
bash install.sh
```

گزینهٔ **۱: Update & Deploy** کد را دریافت و بک‌اند و داشبورد را با هم می‌سازد.
اگر منوی قدیمی از قبل باز بوده، پس از آپدیت از آن خارج شوید و دوباره `bash install.sh` را اجرا کنید تا نسخهٔ جدید منو بارگذاری شود.
گزینهٔ **۲** فقط کد روی دیسک را می‌سازد؛ گزینهٔ **۳** فقط کانتینرها را restart می‌کند و تغییرات کد یا داشبورد را اعمال نمی‌کند.
گزینهٔ جدید **۱۳** تنظیمات، سلامت سرویس‌ها، دسترسی API به دیتابیس، پاسخ داشبورد و تطابق نسخهٔ ایمیج با سورس را بررسی می‌کند.

همین بررسی از خط فرمان:

```bash
bash deploy.sh check
```

## رفتار آپدیت

- منبع آپدیت، شاخهٔ پیش‌فرض واقعی `origin` است؛ در این مخزن فعلاً `master`. نام شاخه دیگر ثابت فرض نمی‌شود و شاخهٔ محلی کاربر هم منبع آپدیت را تعیین نمی‌کند.
- برای انتخاب آگاهانهٔ شاخهٔ دیگری، متغیر `TSB_DEPLOY_BRANCH` را در محیط شل تنظیم کنید؛ مثلاً `TSB_DEPLOY_BRANCH=main bash install.sh`. فایل `.env` برای این انتخاب به‌عنوان کد شل اجرا نمی‌شود.
- دریافت شاخه برای cloneهای shallow و single-branch هم کار می‌کند. خطای شبکه یا شاخهٔ ناموجود پیش از جابه‌جایی کد، آپدیت را متوقف می‌کند.
- کامیت قبلی در `refs/tsb-backups/pre-update-*` حفظ می‌شود. تغییرات محلی کد و فایل‌های untracked غیرعملیاتی با `git stash` ذخیره می‌شوند و خودکار روی نسخهٔ جدید اعمال نمی‌شوند. برای بازبینی از `git stash list` و `git stash show -p` استفاده کنید.
- `.env`، `.env.bak*`، `backups/`، `ready_configs/` و لاگ‌ها از پاک‌سازی و stash کنار گذاشته می‌شوند. دیگر `git clean` در مسیر آپدیت اجرا نمی‌شود.
- در نصب بدون متادیتای Git هم همگام‌سازی snapshot مسیرهای عملیاتی شناخته‌شده را حفظ می‌کند؛ سورس قدیمی جایگزین می‌شود. برای نصب Git موجود، متادیتای آن با یک clone تازه بازنویسی نمی‌شود.
- نصب و دیپلوی با قفل مشترک `/run/telegramsellbot-update.lock` از اجرای هم‌زمان جلوگیری می‌کنند. پردازش deploy فرزند، قفل آپدیت را به ارث می‌برد.

## مراحل دیپلوی کامل

۱. بررسی Docker و اعتبار Compose بدون چاپ تنظیمات حاوی رمز؛ ساخت بک‌اند و داشبورد و تأیید وجود فایل اصلی داشبورد، در حالی که سرویس فعلی هنوز فعال است.

۲. راه‌اندازی و انتظار برای آماده‌شدن PostgreSQL و Redis.

۳. توقف موقت برنامه‌ها و autoheal، سپس تهیهٔ dump دیتابیس و کپی `.env` در `backups/predeploy-*`. فایل‌ها با دسترسی محدود ساخته می‌شوند؛ خطای بک‌آپ مانع تغییر schema می‌شود و کانتینرهای موجود دوباره start می‌شوند.

۴. اجرای bootstrap و migrationها با همان ایمیج ساخته‌شده، بدون بالا آوردن خودکار برنامه در طول migration. PostgreSQL برای آزادکردن قفل‌ها restart نمی‌شود و کانتینرهای دیگر به‌اجبار حذف نمی‌شوند.

۵. ایجاد کانتینرهای برنامه با ایمیج ساخته‌شده؛ بیلد تکراری انجام نمی‌شود.

۶. تأیید healthcheck هر سه برنامه، پاسخ `/healthz` و `/dashboard/` و تطابق revision ایمیج‌ها با سورس. سپس autoheal فعال می‌شود و `.deployed-revision` ثبت می‌شود. پایان `compose up` به‌تنهایی موفقیت محسوب نمی‌شود.

مهلت بررسی سلامت به‌صورت پیش‌فرض ۱۸۰ ثانیه است؛ با `TSB_HEALTH_TIMEOUT` در محیط شل، عددی از ۱ تا ۹۰۰ ثانیه می‌توان تعیین کرد.
نسخهٔ ایمیج API در سربرگ منوی نصب هم نمایش داده می‌شود. ایمیج‌های قدیمی بدون label تا پیش از اولین دیپلوی کامل جدید قابل تأیید نسخه نیستند.

بعد از شروع تغییرات schema، در صورت خطا rollback خودکار دیتابیس انجام نمی‌شود؛ مرحلهٔ خطا اعلام می‌شود و باید پس از رفع علت، دیپلوی را دوباره اجرا کرد. snapshotهای پیش از دیپلوی جایگزین بک‌آپ جامع پروژه نیستند؛ حذف خودکار هم ندارند و فضای دیسک باید مدیریت شود.

## اعتبارسنجی

تست‌های مستقل، عملیات واقعی Git را روی مخزن موقت و دیپلوی را با Docker شبیه‌سازی‌شده اجرا می‌کنند: انتخاب شاخه، حفظ تغییرات، خطای دریافت، خطای بیلد/داشبورد/بک‌آپ/migration، ایمیج قدیمی و شکست سلامت. تست قفل واقعی و حفاظت rsync مخصوص محیط Linux است.
بررسی syntax چهار فایل Bash هم در همین مجموعه انجام می‌شود.

```bash
python -m pytest tests/test_installer_operations.py -q
```

اجرای واقعی Docker و migration روی سرور production در محیط توسعه انجام نشده است؛ این تغییرات روی GitHub منتشر می‌شوند و اجرای آپدیت روی سرور به عهدهٔ اپراتور است.
