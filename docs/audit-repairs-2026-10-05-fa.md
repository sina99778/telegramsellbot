# گزارش اصلاحات بررسی کد — ۵ اکتبر ۲۰۲۶

اصلاحات دو گزارش بررسی در کد پروژه اعمال شدند. تغییرات قبلی موجود در workspace حفظ شدند. این گزارش وضعیت پیاده‌سازی و دامنهٔ تست را توضیح می‌دهد؛ تضمین نبود تمام باگ‌های احتمالی یا رفع قطعی اختلال سرور واقعی نیست.

## اصلاحات امنیتی، مالی و اجرایی

| شمارهٔ گزارش اولیه | مشکل | اصلاح پیاده‌سازی |
|---|---|---|
| ۱ | شارژ کیف پول صرفاً با عکس رسید و گذشت زمان | worker قدیمی فقط یادآوری بررسی بانکی می‌فرستد؛ هیچ پرداخت یا کیف پولی را تأیید نمی‌کند. زمان بارگذاری رسید در ربات و مینی‌اپ ثبت می‌شود. |
| ۲ | مصرف چندبارهٔ تراکنش کریپتو و برخورد مبلغ دو فاکتور هم‌زمان | جدول دائمی crypto_transaction_claims با کلید ترکیبی شبکه و هش؛ ثبت اتمیک پیش از شارژ؛ حفظ هش پس از حذف پرداخت؛ یکسان‌سازی نام‌های TRX/TRON و USDT TRC20، همچنین قالب هش TON؛ قفل تراکنشی برای انتخاب مبلغ یکتا. |
| ۳ | اطلاعات ورود مینی‌اپ در URL و لاگ | درخواست‌های JSON، فرم و QR از هدر استفاده می‌کنند؛ QR با POST و blob محلی نمایش داده می‌شود. توکن لینک ربات به fragment منتقل شده و پس از ذخیره در sessionStorage از آدرس پاک می‌شود. backend توکن‌های query را برای احراز هویت نمی‌پذیرد. |
| ۴ | دسترسی لینک امضاشده به سرویس لغوشده/منقضی یا کاربر مسدود | اعتبار وضعیت اشتراک، زمان پایان و وضعیت صاحب حساب پیش از ارائهٔ کانفیگ بررسی می‌شود. |
| ۵ | فشار ورود داشبورد با تغییر نام کاربری و توقف event loop هنگام scrypt | محدودیت هم‌زمان IP، حساب و کل سامانه؛ بررسی و ارتقای رمز در thread pool با حداکثر دو محاسبهٔ موازی. ظرفیت fallback حافظه محدود شد. |
| ۶ | ارسال بی‌حد درخواست پشتیبانی و تزریق HTML | محدودیت نرخ روی یادداشت، گزارش و درخواست اقدام؛ محدودیت جداگانه برای تکرار درخواست همان سرویس؛ escape متن توضیحات پیش از ارسال به Telegram. این محدودیت زمانی است، نه گردش‌کار دائمی حل تیکت. |
| ۷ | عبور خرید هم‌زمان از ظرفیت سرور | قفل PostgreSQL مشترک برای همان سرور پیش از شمارش؛ درخواست هم‌زمان به‌صورت سریع رد می‌شود. مسیر ساخت، انتقال عادی و انتقال سرویس واردشده از ربات قدیمی پوشش داده شدند. ظرفیت کاربران ساخته‌شده خارج از ربات همچنان تابع اطلاعات ثبت‌شده و همگام‌سازی است. |
| ۸ | نادیده‌گرفتن تخفیف شخصی در مینی‌اپ | محاسبهٔ مشترک قیمت در نمایش پلن، کیف پول و درگاه‌ها؛ خرید دلخواه نیز تخفیف را در قیمت نهایی می‌گیرد. مبلغ فاکتور در مسیر تأیید دوباره تخفیف نمی‌خورد. |
| ۹ | شکست خرید با تخفیف ۱۰۰٪ | ساخت سفارش رایگان بدون تراکنش صفر در کیف پول؛ مسیر درگاهِ خرید رایگان به تکمیل خرید از مسیر کیف پول هدایت می‌شود. کنترل موجودی پلن و ساخت کانفیگ برقرار است. |
| ۱۰ | نمایش ۱۰ یا ۱۰۰ گیگ به‌صورت ۱ گیگ در خرید دلخواه | حذف حذف‌کردن صفرهای صحیح از نام حجم با قالب‌بندی Decimal. |
| ۱۱ | خطای ۵۰۰ برای timestamp بسیار بزرگ و پذیرش زمان آینده | مدیریت OverflowError و OSError، رد زمان بیش از ۶۰ ثانیه در آینده و بررسی ساختار JSON کاربر. |

محدودیت ارسال هش و عکس رسید اضافه شد؛ خواندن فایل آپلودی فقط تا سقف اندازهٔ مجاز به‌علاوهٔ یک بایت انجام می‌شود. شکست تأیید دستی کریپتو transaction را rollback می‌کند تا پرداختِ ردشده اشتباهاً تأییدشده باقی نماند.

## اصلاحات اتصال پنل

| ایراد گزارش پنل | اصلاح پیاده‌سازی |
|---|---|
| نشست منقضی با HTML ورود یا JSON success=false | تشخیص پاسخ ورود و احراز هویت دوباره در همان آدرس؛ پاسخ HTML نامرتبط باعث تکرار عملیات نوشتن نمی‌شود. |
| موفق شمردن login با کوکی قبلی باوجود success=false | پاک‌کردن کوکی قبلی و اعتبارسنجی نتیجهٔ ورود؛ پاسخ رد ورود بر وجود کوکی اولویت دارد. |
| ۴۰۴ احراز هویت در add/delete و اشتباه‌گرفتن آن با حذف کانفیگ | بررسی خواندنی API پیش از تکرار نوشتن؛ ۴۰۴ مبهم به‌عنوان حذف موفق یا کانفیگ ناپدیدشده گزارش نمی‌شود. |
| login هم‌زمان روی کلاینت مشترک | قفل ورود و شمارهٔ نسل نشست برای Sanaei و Rebecca؛ درخواست‌های هم‌زمان یک بازیابی مشترک دارند. |
| تکرار کور نوشتن پس از ۵۰۰ یا timeout | عملیات غیرقابل‌تکرار Sanaei پس از خطای مبهم تکرار نمی‌شود؛ Rebecca نیز تنها خواندن‌ها را خودکار تکرار می‌کند. اتصالِ قطعاً ارسال‌نشده در Sanaei همچنان امکان تلاش دوباره دارد. |
| قبول صفحهٔ ورود به‌عنوان backup دیتابیس | بررسی امضای SQLite و حداقل اندازه؛ صفحهٔ HTML یا فایل فاقد امضای SQLite رد می‌شود. این بررسی معادل integrity_check کامل دیتابیس نیست. |
| بسته‌شدن کلاینت در حال استفاده با تغییر تنظیمات | شمارش استفاده‌کنندگان و بستن پس از خروج آخرین درخواست؛ خطای عملیات، کلاینت را برای درخواست بعدی بازنشسته می‌کند و اتصال تازه بدون تغییر URL ساخته می‌شود. |

پیش‌بررسی خرید Sanaei اکنون دسترسی واقعی به لیست اینباند را بررسی می‌کند. health check هر ۱۰ دقیقه اجرا می‌شود؛ سه شکست متوالی تقریباً در ۲۰ تا ۳۰ دقیقه شناسایی می‌شوند. اعلان سلامت HTML امن دارد. تغییر خودکار HTTPS به HTTP هنگام ثبت Sanaei حذف شد؛ انتخاب صریح مدیر محترم است. redirect از اتصال HTTPS به HTTP پیش از ارسال درخواست رد می‌شود تا اطلاعات ورود روی HTTP ارسال نشود.

پشتیبانی بازیابی CSRF با endpoint /csrf-token و هدر X-CSRF-Token، از جمله پس از تجدید نشست، اضافه شد. مرجع سازگاری: [مستندات رسمی احراز هویت Sanaei](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/reference/api/authentication.mdx).

## تست و محدودیت اعتبارسنجی

- کل تست‌های Python: **۷۵۶ موفق، ۲ اجرا نشده**. هشدارهای pytest باقی مانده‌اند؛ عمدتاً از mockها و بخش‌های پیشین هستند.
- ۴۵ مورد پذیرش جدید در test_audit_repairs.py، شامل انقضای نشست، ورود هم‌زمان، ۴۰۴ مبهم، CSRF پس از ورود مجدد، عدم تکرار نوشتن، pool، هش مشترک شبکه، خرید رایگان و لغو دسترسی لینک اشتراک.
- compileall برای apps/core/models/schemas/services/scripts موفق است؛ import ماژول‌های API و worker نیز موفق بود.
- node --check برای api.js و pages.js موفق است.
- npm run build داشبورد با بررسی TypeScript و Vite موفق است.
- Docker daemon محلی در دسترس نبود. دو تست PostgreSQL در test_audit_postgres.py اجرا نشدند؛ آن‌ها فقط schema آزمایشی با نام یکتا ایجاد و حذف می‌کنند. برای اجرا در محیط آزمایشی، AUDIT_TEST_DATABASE_URL را به دیتابیس مصرفی تست تنظیم کنید و python -m pytest -q tests/test_audit_postgres.py را اجرا کنید.
- تست‌ها روی Python محلی 3.10 اجرا شدند؛ تصویر تولید پروژه Python 3.12 است و build تصویر Docker اینجا تأیید نشده است.
- اتصال به پنل واقعی شما، لاگ زمان قطع، TLS، reverse proxy، restart سرور و تراکنش بانکی واقعی بررسی عملی نشده‌اند. نسخهٔ دقیق Sanaei مشخص نیست؛ رفع تمام عوامل احتمالی قطع روزانهٔ سرور واقعی هنوز قابل ادعا نیست.

## استقرار و تغییر رفتار

migration جدید scripts/migrations/006_crypto_transaction_claims.py باید پیش از شروع workerهای نسخهٔ جدید اجرا شود. deploy.sh آن را از فهرست migrations اجرا می‌کند. این migration هش پرداخت‌های تاریخیِ شارژشده را ثبت می‌کند و موارد تکراری یا بدون هش را برای رسیدگی دستی لاگ می‌کند؛ موجودی تاریخی را خودسرانه اصلاح نمی‌کند. اگر نصب با روشی غیر از deploy.sh به‌روز می‌شود، همین ترتیبِ migration پیش از worker لازم است.

کلید تنظیمات قدیمی card_autoconfirm برای سازگاری حفظ شده، اما معنای آن اکنون «یادآوری بررسی رسید» است. تأیید بانک و شارژ کیف پول با اقدام مدیر انجام می‌شود. کلاینت‌های شخصی مینی‌اپ که به _auth یا _session در query وابسته بوده‌اند باید به هدرهای X-Telegram-Init-Data یا X-Miniapp-Session مهاجرت کنند. صفحهٔ مینی‌اپ را پس از استقرار تازه بارگذاری کنید تا JS قدیمی استفاده نشود.

فایل docs/repro_panel_connections.py اکنون تست‌های رفتار اصلاح‌شده را اجرا می‌کند و دیگر انتظارِ وقوع باگ قبلی را ندارد.
